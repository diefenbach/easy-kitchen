EasyKitchen Python/Django review — 2026-11-09

Overall assessment
==================
The application has an appropriate Django-first architecture: ordinary models,
forms and class-based views, shared business services, and thin REST/MCP adapters.
Owner-scoped application lookups, authenticated REST defaults, database uniqueness
constraints and a substantial test suite provide a good foundation. The main
weakness is inconsistent write discipline: REST/MCP services, web ModelForms and
model save hooks use different validation and concurrency rules. Green tests do
not currently establish safe concurrent writes or web/import compatibility.

This review found no critical issue within the reviewed scope. Findings below
include two high-priority issues, eight medium-priority issues and two low-
priority issues. Severity reflects practical impact, not code style.

Scope and environment actually reviewed
======================================
Reviewed the current working tree, including its pre-existing uncommitted changes;
this is not a review of main alone. No application code was changed for the review.

Declared Python: >=3.10; installed Python: 3.13.3. Declared Django: >=5.2,<5.3;
installed Django: 5.2.18. Installed DRF: 3.16.1; MCP SDK: 2.3.0; psycopg: 3.3.6.
CI and the Docker image target Python 3.13. Other declared Python versions were
not exercised.

Structure: src/project contains settings, URL routing and entry points;
src/easy_kitchen contains models, forms, web/planner/recipe views, services,
presenters, validation, REST serializers/viewsets and the MCP server. Templates
and static assets implement a server-rendered interface. Unit/integration tests
live under src/easy_kitchen/tests; browser journeys live under e2e.

Tools: uv/uv.lock, Ruff, pytest, pytest-django, pytest-xdist, pytest-playwright,
drf-spectacular, Sphinx/MyST, PostgreSQL, Gunicorn and Docker. Test settings use
SQLite by default; separate PostgreSQL test settings exercise database behavior.

Reviewed models and core create/update/delete/reorder/import/planner services;
web forms and editor save paths; REST authentication, serializers and viewsets;
MCP authentication, validation and service dispatch; presenters; PDF generation;
admin configuration; settings, entry points, Docker and repository deployment/CI
configuration. Followed relevant templates and selected permission, parity,
query and write-integrity tests. Inspected the historical migration cited below.
Executed the full existing test suite, but did not inspect every test assertion,
every migration or every browser JavaScript path line by line.

Findings in priority order
==========================

HIGH

H2. Individual catalog updates acquire locks in the opposite order to batch saves
Status: confirmed PostgreSQL deadlock for articles; analogous department risk.
Location: src/easy_kitchen/services.py:479, :488, :353;
          src/easy_kitchen/services.py:495, :500, :382.
Problem: update_owned_article() first locks one article, then save_articles()
locks the user's entire article catalog. Two requests editing different rows can
each hold a row needed by the other. Department updates repeat this pattern.
Evidence: Two PostgreSQL connections updated Alpha and Beta respectively. A
barrier after _validate_update() ensured each already held its individual row
lock before proceeding into save_articles(). PostgreSQL reported "deadlock
detected" for one transaction. The barrier controls scheduling; it does not
change the locking operations. The department case was not separately executed.
Impact: Legitimate concurrent REST/MCP edits can fail; the victim transaction
rolls back. The REST ServiceErrorsMixin handles ServiceError, not PostgreSQL's
OperationalError, so this is not converted to a normal validation response.
Smallest improvement: Acquire the required catalog locks once, in a consistent
primary-key order, before taking any individual catalog lock. Alternatively,
make single-record edits genuinely single-record operations with appropriate
uniqueness-error handling. Keep batch name-swap behavior intact. Add a real
PostgreSQL two-connection regression for articles and departments.

H3. The production image defaults to Django's development server and settings
Status: confirmed repository configuration defect; live deployment exposure unknown.
Location: Dockerfile:3-7, :20; src/manage.py:7;
          src/project/settings/development.py:19;
          src/project/settings/base.py:5.
Problem: The image runs "python manage.py runserver 0.0.0.0:8000" and does not
set DJANGO_SETTINGS_MODULE. manage.py therefore selects development settings,
which enable DEBUG. The base secret also has a public development fallback.
Production's mandatory-secret checks and secure-cookie/TLS settings are bypassed
unless deployment explicitly overrides the settings module.
Impact: An image started using its defaults is unsuitable for production. If a
deployment supplies routable allowed hosts but omits the settings override,
debug responses may disclose internals and production security settings are
absent. Default development allowed hosts restrict exposure; this review does
not establish that the live service currently exposes debug pages.
Smallest improvement: Set the image's settings module to project.settings.production
and default to the already installed Gunicorn with project.wsgi:application.
Keep local development's runserver command separate and preserve explicit MCP
entry-point overrides. Check the external production Compose configuration and
add a small image/entry-point configuration check. That external stack was not
available for this review.

MEDIUM

M1. Inline editor formsets accept the same existing row ID more than once
Status: confirmed validation/data-loss bug.
Location: src/easy_kitchen/forms.py:513-539, :544-558.
Problem: add_fields() limits IDs to the correct parent, but the formset does not
reject duplicate IDs. save_ordered() then saves multiple forms to the same row.
Evidence: A two-ingredient formset containing the first ingredient's ID in both
forms passed is_valid(). The second form overwrote the first edit; the original
second ingredient remained unchanged. Parent scoping prevents cross-owner IDs
but does not establish that submitted rows are distinct.
Impact: An invalid or duplicated draft payload succeeds while silently dropping
edits. The shared formset also serves recipe steps and shopping items.
Smallest improvement: Add a formset clean() check for repeated existing IDs,
including conflicting delete/edit submissions. Preserve the existing parent-
scoped queryset. Add duplicate-ID and delete/edit conflict regressions.

M2. Web recipe validation permits data rejected by the application's own import
Status: confirmed round-trip bug; related step-field mismatch traced.
Location: src/easy_kitchen/forms.py:343-365, :549-552;
          src/easy_kitchen/api/serializers.py:282, :294;
          src/easy_kitchen/validation.py:13-14;
          src/easy_kitchen/recipe_views.py:140.
Problem: RecipeForm's generated description TextField has no 5,000-character
limit, whereas the API/import serializer does. The inline step editor similarly
lacks the serializer's 2,000-character limit. Direct ModelForm saves bypass
shared service validation.
Evidence: A RecipeForm accepted and saved a 5,001-character description. Export
via recipe_export_data(), followed by ImportForm validation of that export,
failed. The description mismatch was executed; the step mismatch is supported
by the field definitions but was not separately executed.
Impact: Valid web-created recipes cannot reliably be backed up and restored or
used through the other interfaces.
Smallest improvement: Apply the same shared field limits to web forms/formsets
and serializers, and choose an explicit policy for already stored longer text.
Test web-save -> export -> import at and beyond the accepted boundaries.

M3. Unchanged articles are always rewritten, with extra department queries
Status: confirmed incorrect change detection and measured redundant writes.
Location: src/easy_kitchen/services.py:353, :368-376.
Problem: Change detection compares existing.department (a model object or None)
with record["department"] (a code string). These are unequal even when the
department has not changed. Accessing the relation on the unjoined queryset
also adds a query for each assigned existing article considered.
Evidence: Saving one unchanged Milk/dairy record issued two UPDATE statements
(temporary UUID name and final save), eight SQL statements overall, and changed
updated_at. This is caused by representation mismatch, not a missing index.
Impact: Saving a large unchanged draft performs avoidable work, extends lock
holding and makes timestamps unreliable indicators of a meaningful edit.
Smallest improvement: Compare normalized scalar values: department_id against a
resolved target ID, or department_code against a normalized code with a joined
department queryset. Reuse resolved departments. Add a no-op regression that
asserts no UPDATE and preserves updated_at.

M4. Django admin exposes other owners' records to ordinary permitted staff
Status: confirmed behavior; security severity depends on the intended staff model.
Location: src/easy_kitchen/admin.py:26-28, :42-45, :49-53;
          contrast DepartmentAdmin's owner filter at :12-16.
Problem: Article, Recipe and ShoppingList use unrestricted ModelAdmin querysets
and owner fields. DepartmentAdmin alone scopes records to request.user.
Evidence: A non-superuser staff account granted only shopping.view_recipe could
open the recipe admin changelist and see another user's private recipe title.
This required authenticated staff access; no public or normal-user bypass was
found. Default change permissions likewise operate on the unrestricted queryset.
Impact: This violates the stated all-data-is-user-scoped convention if staff
accounts are intended to remain tenant-scoped. If staff are deliberately global
operators, that trust boundary needs an explicit documented exception.
Smallest improvement: Apply the existing owner-scoping pattern consistently,
set ownership on creation and restrict related-field/inline department choices.
If global administration is intentional, document that exception and test it
instead. Do not infer public exposure from this finding.

M5. New-record positioning has no stable lock when a collection is empty
Status: confirmed PostgreSQL ordering race.
Location: src/easy_kitchen/models.py:11-16, :83-86, :199-202.
Problem: _place_new_record_first() updates existing owner rows and then inserts
at position 1. With no existing rows, there is nothing to lock. Wrapping each
save in atomic() does not serialize the two transactions.
Evidence: Two PostgreSQL connections created the first two recipes concurrently,
with a barrier after the positioning UPDATE and before INSERT. Both committed
with position=1. Ordering uses (position, id), so the fallback does not guarantee
the intended new-record-first order. ShoppingList shares the same helper; that
variant was not independently executed.
Impact: Concurrent creates produce ambiguous positions and can violate the
documented ordering behavior. Records themselves are retained; this is not
evidence of lost recipe content.
Smallest improvement: Serialize owner-collection position allocation using a
stable existing row, such as the owner, before updating positions. Use the same
lock order for create/import/reorder operations. A unique position constraint
alone would turn the race into a failed create rather than solve it.

M6. Opening the list editor performs one department lookup per assigned item
Status: measured N+1 query issue.
Location: src/easy_kitchen/forms.py:528, :556-558;
          src/easy_kitchen/models.py:109-111;
          src/easy_kitchen/views.py:222-224.
Problem: Each inline form reads instance.department_code, which dereferences
department. The formset's item queryset does not join that relation. Caching
department choices does not cache the department on each ShoppingItem instance.
Evidence: An authenticated GET for an editor containing five dairy items issued
five individual department-by-ID SELECTs, twelve SQL statements overall.
Impact: Editor query count grows with the number of assigned items, including
repeated queries for the same department.
Smallest improvement: Supply a select_related("department") item queryset to
the formset, while retaining the existing parent/owner restrictions. Add a
bounded query-count test comparing a small and a larger assigned-item list.

M7. The planner evaluates the full recipe catalog independently for each day
Status: measured repeated-query/serialization issue.
Location: src/easy_kitchen/planner_views.py:53-75;
          src/easy_kitchen/forms.py:465-467.
Problem: Each of seven MealPlanDayForm instances gets its own recipe queryset.
Rendering their select widgets evaluates the catalog repeatedly; autocomplete
search data loads it again.
Evidence: Rendering a blank week with one available recipe performed eight recipe
SELECTs and twelve SQL statements overall. The seven select widgets also repeat
recipe options in the response. No production latency measurement was made.
Impact: Database work, object creation and output size increase unnecessarily
with the recipe catalog; this is more relevant for users with many recipes.
Smallest improvement: Materialize the owned recipe choices once per request and
reuse them for rendering/search data. Preserve a user-filtered ModelChoiceField
queryset for submitted-value validation. Share evaluated data, not a global cache
or a new repository abstraction. Verify bounded catalog reads in a GET test.

M8. A historical data migration imports a mutable runtime service helper
Status: substantiated maintenance/reproducibility risk; not currently failing.
Location: src/easy_kitchen/migrations/0005_recipeingredient_name_quantity.py:5-9;
          src/easy_kitchen/services.py:765.
Problem: The historical ingredient conversion imports _ingredient_name_and_quantity
from the current services module. Renaming/removing that private helper, changing
its behavior or changing runtime imports can break replay of the old migration
or change the conversion performed on an old database.
Impact: Fresh installations and upgrades from pre-0005 databases depend on future
application implementation details. Current migration execution passes; an old
database populated with historical ingredient examples was not replayed here.
Smallest improvement: Freeze the small pure parser inside the migration, keeping
apps.get_model() for historical models. Test representative old ingredient
values through the migration before removing the runtime helper if it is unused.

LOW

L1. The hide-completed endpoint coerces malformed JSON values to booleans
Status: confirmed input-validation bug; normal browser requests are unaffected.
Location: src/easy_kitchen/views.py:100-104.
Problem: bool(payload["hide"]) interprets any nonempty string as True instead of
requiring a JSON boolean.
Evidence: An authenticated POST with {"hide": "false"} returned 204 and persisted
hide_completed_items=True.
Impact: Incorrect clients can successfully request the opposite state from the
one they intended, rather than receiving a clear validation error.
Smallest improvement: Require isinstance(value, bool), returning HTTP 400 for
other types, and test true/false plus string/null/number inputs. Reuse an existing
strict boolean validator if practical; no generalized validation framework is
needed for this endpoint.

L2. Web editor saves can overwrite concurrently changed, non-editable fields
Status: confirmed concurrency edge case; optional robustness improvement.
Priority revised after discussion: ordinary ModelForm.save() is idiomatic Django;
this narrow overlap is unlikely in a small application and does not justify
high-priority conflict management. Production frequency has not been measured.
Location: src/easy_kitchen/recipe_views.py:133, :139-142;
          src/easy_kitchen/views.py:227, :232-234;
          src/easy_kitchen/forms.py:354-365.
Problem: The views load model instances and validate forms before opening the
transaction, then call ModelForm.save() without restricting update_fields. Django
writes fields that are not exposed by the form too. Atomicity of the subsequent
save does not make the earlier snapshot current or prevent lost updates.
Evidence: Instantiate and validate a RecipeForm, set the same recipe's favorite
to True through set_owned_recipe_favorite(), then save the form. The persisted
favorite becomes False again, although favorite is absent from RecipeForm. This
models an interleaving during a POST, not merely a stale browser tab. List saves
have the same structure and can overwrite hide_completed_items or position;
those variants were traced but not separately reproduced.
Impact: One interface silently undoes a successful action from another request.
Smallest improvement: Persist only the fields the editor owns, with explicit
update_fields or the existing partial-update service. Include updated_at and
preserve image-clear/upload behavior. If child edits must also be serialized,
define one parent-lock protocol for their writers. Add a regression that
interleaves a favorite/state update between form construction and persistence.

Architecture, security and tests: assessment beyond the findings
===============================================================
Keep the existing Django-first structure. There is no demonstrated need for a
repository layer, generic operation framework or wholesale service rewrite.
Useful existing service annotations and domain errors make the adapters easier
to follow. The concrete maintainability improvements are aligning web writes
with shared validation/partial updates, simplifying single-row catalog updates,
and making transaction ownership explicit. No naming-only or type-annotation-
only changes are requested by this review.

The reviewed ordinary web/REST/MCP paths derive ownership from the authenticated
user and filter object lookups accordingly. REST defaults require authentication
and provide token/session authentication. Django CSRF middleware is enabled;
the admin exception is described separately above. No runtime raw SQL injection
path, unconditional template safe-marking or external-image fetch in the PDF
path was identified. PDF text is escaped and uploaded images use the local file
path. These observations are scoped code review results, not penetration-test
or comprehensive vulnerability-scan claims.

Existing FK indexes and explicit uniqueness constraints already cover important
relationships, including per-user article names, department codes and meal-plan
dates. The observed performance problems are repeated queries or wrong change
detection. There is no measured query plan justifying an additional index here.

The existing tests provide meaningful assurance for ordinary CRUD, authentication,
ownership, interface parity, validation, imports and browser interactions. The
full suite passes, but the independent probes below all demonstrate behavior
not prevented by that suite. Convert their scenarios into regression tests when
fixing the findings, especially concurrent transactions on PostgreSQL. SQLite
success is not evidence of correct select_for_update behavior.

Three most important next steps
==============================
1. Fix catalog lock ordering and owner-collection position allocation; add real
   PostgreSQL concurrency regressions for the reproduced failures.
2. Make the Docker default explicitly production-safe, then verify the actual
   external deployment settings and decide/document the intended admin trust
   boundary before changing staff permissions.
3. Reject duplicate inline IDs and align web/export/import validation boundaries.
   Treat restricting unrelated editor fields as a lower-priority robustness task.
